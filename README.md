# AI 국내 여행 플래너 V2 — TripAI

여행 날짜와 취향을 입력하면 AI가 국내 여행 지역을 추천하고, Kakao Local의 실제 장소 정보를 바탕으로 하루 일정을 구성하는 반응형 웹 서비스입니다.

## 2. 프로젝트 개요

### 2.1 배경

기존 `travel_planner.py`는 날짜를 입력하면 AI가 국내 여행지를 추천하고 Kakao Local API로 장소를 검색한 뒤 여행 리포트를 만드는 CLI 프로그램이었습니다. 이번 프로젝트에서는 이 흐름을 순수 HTML·CSS·JavaScript 프론트엔드와 Python FastAPI 백엔드로 확장하여, 브라우저에서 직접 사용할 수 있는 웹 서비스로 구현했습니다.

### 2.2 목적

여행 날짜는 정했지만 목적지를 고르지 못한 사용자가 여러 지역, 관광지, 맛집을 따로 검색하고 일정을 조합하는 시간을 줄이는 것이 목적입니다.

```text
날짜와 취향 입력
→ AI가 국내 여행 지역 추천
→ 실제 장소 정보 검색
→ AI가 오전·오후·저녁 일정 구성
→ 하나의 여행 플랜으로 제공
```

### 2.3 대상 사용자

- 국내 단기·주말 여행지를 아직 정하지 못한 사용자
- 여행지 검색과 비교에 쓰는 시간을 줄이고 싶은 사용자
- 익숙하지 않은 국내 여행지를 새롭게 추천받고 싶은 사용자
- 실제 관광지와 맛집을 포함한 하루 일정을 빠르게 만들고 싶은 사용자

### 2.4 핵심 가치

AI의 추천 능력만 사용하는 것이 아니라 Kakao Local의 실제 장소 검색 결과를 함께 사용합니다. AI는 지역과 일정을 구성하고, 외부 장소 데이터는 구체적인 관광지·음식점 정보를 보강하는 역할을 맡습니다.

## 5. 주요 기능

### 5.1 입력과 이중 검증

프론트엔드와 백엔드가 각각 입력값을 검증합니다.

- 프론트엔드: 날짜 필수 입력, 오늘부터 1년 이내 범위 확인
- 백엔드: JSON 구조, 날짜 형식·범위, 허용된 동행·스타일 값 확인
- 중복 스타일은 입력 순서를 유지하면서 제거
- 잘못된 요청은 내부 예외 대신 사용자용 오류 코드와 문구로 반환

### 5.2 선택 가능한 동행

동행 UI는 체크박스를 사용하지만 JavaScript가 한 번에 하나만 선택되도록 제어합니다. 같은 항목을 다시 누르면 선택이 해제되어 `companion: null`로 요청할 수 있습니다.

### 5.3 복수 여행 테마

여행 스타일은 여러 개를 동시에 고를 수 있습니다. 선택값은 `styles` 배열로 전송되며, 아무것도 고르지 않으면 빈 배열로 전달되어 날짜와 계절성을 중심으로 추천합니다.

### 5.4 단계별 로딩과 중복 요청 방지

요청 중에는 생성 버튼을 비활성화하고 다음 안내 문구를 시간 순서로 보여줍니다.

```text
여행 조건을 확인하고 있습니다...
AI가 어울리는 여행지를 분석하고 있습니다...
추천 지역의 실제 장소를 찾고 있습니다...
여행 일정을 구성하고 있습니다...
```

이 문구는 실제 서버 진행률이 아니라 긴 대기 시간 동안 현재 작업 내용을 알려주는 UX입니다. 브라우저 요청은 60초를 넘으면 중단하고 재시도 안내를 표시합니다.

### 5.5 AI 여행 지역 추천

Naito API의 `gpt-5.5` 모델에 날짜, 동행, 여행 스타일을 전달하여 다음 세 필드를 생성합니다.

```json
{
  "recommended_city": "광역자치단체명을 포함한 시·군·구",
  "reason": "추천 이유",
  "seasonal_tip": "여행 시기 참고사항"
}
```

응답은 JSON 파싱 후 정확한 키·자료형·빈 값 여부·국내 광역자치단체명 포함 여부를 검사합니다. 검증에 실패하면 더 제한적인 프롬프트로 한 번 재요청하고, 다시 실패하면 안전한 오류 응답을 반환합니다.

### 5.6 실제 장소와 맛집 검색

추천 지역을 기준으로 Kakao Local API를 호출합니다.

- 선택한 일반 테마별 장소 검색
- 부족한 추천 장소를 `지역 + 관광명소` 검색으로 보충
- 최대 5개의 추천 장소 구성
- `지역 + 맛집` 검색으로 별도 맛집 목록 구성
- 장소명, 주소, 카테고리, Kakao 장소 URL, 좌표를 정규화
- 외부 API 일부 실패 시 전체 요청을 즉시 중단하지 않고 경고와 가능한 결과를 반환

### 5.7 축제 테마 처리

축제는 상시 존재하는 장소와 달리 날짜에 따라 열리고 닫히는 행사이므로 별도 처리를 적용했습니다.

- AI가 추천 이유에서 구체적으로 언급한 축제명과 Kakao 검색 결과의 이름이 일치하는 후보만 채택
- 축제 장소는 최대 2개로 제한
- 나머지 추천 장소는 일반 관광명소로 보충
- 적합한 축제를 찾지 못하면 축제를 억지로 채우지 않고, 일반 관광지 중심으로 구성했다는 안내를 여행 시기 정보와 일정에 반영

다만 Naito는 공식 행사 일정 데이터베이스가 아니며 Kakao Local도 특정 날짜의 개최 여부를 검증하는 API가 아닙니다. 현재 로직은 명백히 관련 없는 축제의 혼입을 줄이는 보수적 필터이지, 행사 일정을 공식적으로 확정하는 기능은 아닙니다. 방문 전 공식 홈페이지에서 일정과 운영 여부를 확인해야 합니다.

### 5.8 AI 최종 일정 구성

AI 1단계 결과와 Kakao 장소·맛집 데이터를 다시 Naito API에 전달하여 다음 구조의 일정을 만듭니다.

```json
{
  "title": "여행 제목",
  "morning": "오전 일정",
  "afternoon": "오후 일정",
  "evening": "저녁 일정"
}
```

프롬프트는 입력 데이터에 없는 구체적인 장소를 새로 만들지 않고, 같은 유형의 장소를 반복하지 않으며, 선택 테마와 동행을 반영하도록 제한합니다. 결과 JSON 검증과 1회 재요청이 모두 실패해도 지역·장소 결과를 버리지 않고 기본 일정으로 대체합니다.

### 5.9 결과 화면

JavaScript가 서버 응답을 다음 순서로 렌더링합니다.

- 추천 지역과 이유
- 여행 시기 포인트
- 추천 장소 카드
- 맛집 카드
- 오전·오후·저녁 일정
- 부분 실패 경고

외부에서 받은 문자열은 `innerHTML` 대신 `textContent`를 중심으로 삽입하고, 외부 장소 링크에는 `noopener noreferrer`를 적용했습니다.

### 5.10 다크 모드와 반응형 UX

- 시스템 테마를 초기값으로 사용
- 사용자가 선택한 라이트·다크 모드를 `localStorage`에 저장
- 모바일 햄버거 메뉴와 Escape 키 닫기 지원
- 선택 카드, 버튼, 결과 카드, FAQ의 상태 변화와 애니메이션 구현
- `prefers-reduced-motion: reduce` 환경에서는 애니메이션 시간을 최소화
- 모바일 1열, 태블릿 2열, 데스크톱 최대 3열의 결과 카드 구성

  ▼

## 12. 문제 해결 과정

### 12.1 축제 테마 값이 백엔드에 전달되지 않던 문제

축제 체크박스만 `name="style"`로 되어 있고 JavaScript는 `name="styles"`만 수집하여, 축제를 눌러도 `styles` 배열에 들어가지 않았습니다. HTML 속성 한 글자 차이가 화면 → JavaScript → 백엔드 전체 데이터 흐름을 끊을 수 있다는 점을 확인했고, 현재는 모든 테마가 `name="styles"`를 사용합니다.

### 12.2 날짜와 맞지 않는 축제가 추천되던 문제

Kakao Local의 `지역 + 축제` 검색은 특정 날짜의 행사 개최 여부를 확인하지 않습니다. AI 역시 공식 일정 데이터가 없으면 기억에 의존할 수 있습니다. 현재는 AI 추천 이유에 구체적으로 등장한 축제와 Kakao 장소명이 일치할 때만 최대 2개를 채택하고, 찾지 못하면 일반 관광지를 제공하면서 그 사실을 사용자에게 알립니다.

### 12.3 비슷한 장소가 반복되던 문제

한 지역에서 같은 유형의 장소가 여러 개 검색되면 일정이 단조로워질 수 있었습니다. 최종 일정 프롬프트에 같은 유형을 반복하지 않고 서로 다른 경험을 균형 있게 조합하도록 명시했습니다.

### 12.4 선택을 되돌릴 수 없던 동행 UI

동행을 라디오 버튼으로 구현했을 때는 한 번 고른 뒤 미선택 상태로 돌아갈 수 없었습니다. 체크박스 UI와 JavaScript 단일 선택 제어를 결합하여, 다른 항목 선택 시 기존 항목을 해제하고 같은 항목을 다시 누르면 미선택으로 돌아가도록 개선했습니다.

### 12.5 로컬과 배포 환경의 차이

개발 과정에서 `vercel dev`의 Python 함수 실행이 첫 요청 뒤 종료되며 `ECONNREFUSED` 또는 `FUNCTION_INVOCATION_FAILED`가 발생한 적이 있었습니다. 같은 코드가 FastAPI 개발 서버와 Vercel Production에서는 정상 동작하여, 애플리케이션 오류와 로컬 Vercel 실행 환경의 수명주기 문제를 분리해 확인했습니다.

또한 정적 파일의 `304 Not Modified`는 브라우저 캐시 응답이며 `/api/plan`의 성공·실패 상태와 별개라는 점도 로그를 나누어 확인했습니다.

## 13. 프로젝트의 아쉬운 점과 개선 방향

### 13.1 여러 테마 선택 시 맛집 요소 분리가 부족함

현재 장소 수집 로직은 축제를 제외한 선택 테마를 모두 `지역 + 테마명` 검색어로 사용합니다. 따라서 `맛집(food)`을 다른 테마와 함께 선택하면 `지역 + 맛집` 결과가 일반 ‘추천 장소’ 목록에 들어갈 수 있고, 별도로 실행하는 맛집 검색 결과와 중복되거나 관광지 영역에 음식점이 섞일 수 있습니다.

추천 장소는 음식점이 아닌 관광·문화·자연·체험 장소를 최대한 우선하고, 음식점은 ‘맛집’ 영역에서 명확히 분리하는 편이 서비스 구조에 더 적합했습니다. 개선할 때는 다음 기준을 적용할 수 있습니다.

- `food`를 일반 장소 검색용 테마에서 제외하고 맛집 검색에만 반영
- Kakao 카테고리로 음식점을 판별하여 추천 장소 목록에서 제외
- 추천 장소와 맛집 사이에 장소명·주소 기준의 교차 중복 제거 적용
- 여러 테마를 선택했을 때 비음식점 장소의 유형별 비율을 먼저 배정한 뒤 맛집을 별도 구성

### 13.2 축제 일정의 공식 검증 부재

현재 사용하는 Naito와 Kakao Local만으로는 특정 날짜에 축제가 실제 개최되는지 100% 검증할 수 없습니다. 공식 축제·행사 API를 추가하고 행사 시작일·종료일, 지역, 취소 여부를 확인하는 구조가 필요합니다.

### 13.3 로딩 문구가 실제 서버 진행률은 아님

단계별 문구는 정해진 시간에 바뀌는 대기 안내입니다. 향후 Server-Sent Events, 스트리밍 또는 작업 상태 조회 API를 사용하면 실제 처리 단계와 UI를 일치시킬 수 있습니다.

### 13.4 저장·공유·분석 기능 없음

현재 결과는 브라우저 화면에만 표시되며 여행 계획 저장, 링크 공유, 사용자 기록, 방문자 분석은 구현하지 않았습니다. 이 항목들은 이번 과제의 핵심 범위 또는 선택한 보너스 범위에 포함하지 않았습니다.

### 13.5 자동 배포 연결 확인 필요

Production 배포는 확인했지만 GitHub push와 Vercel 자동 배포의 연결 상태는 현재 자료만으로 확정할 수 없습니다. 제출 전 Vercel의 Git 설정과 최신 커밋 반영 여부를 확인할 필요가 있습니다.

## 14. 이번 과제를 통해 배운 점

### 프론트엔드와 백엔드의 역할 분리

HTML은 구조, CSS는 표현과 반응형, JavaScript는 입력·상태·통신·렌더링, Python은 비밀키 보호와 외부 API 조정을 담당하도록 역할을 나눴습니다.

### 사용자 입력부터 화면 출력까지의 전체 흐름

폼의 선택값이 JavaScript 객체가 되고, JSON 요청으로 Python에 전달되며, AI와 장소 API의 응답이 다시 JSON과 DOM을 거쳐 사용자 화면에 표시되는 전 과정을 연결했습니다.

### API 키를 서버에 두어야 하는 이유

브라우저 JavaScript에 키를 넣으면 누구나 개발자 도구에서 확인할 수 있습니다. 키를 Python 환경 변수로 관리하고 서버가 외부 API를 대신 호출해야 노출 가능성을 줄일 수 있습니다.

### AI 응답은 생성 후 검증해야 함

AI에게 JSON을 요청해도 형식이나 값이 항상 보장되지는 않습니다. 파싱, 스키마 검증, 허용 지역 확인, 1회 재요청, 최종 대체 결과가 필요했습니다.

### 외부 API마다 데이터의 성격이 다름

Kakao Local은 장소 검색에는 유용하지만 행사 개최일 검증 수단은 아닙니다. ‘검색 결과가 존재한다’와 ‘그 날짜에 실제 행사가 열린다’를 구분해야 하며, 공식 일정이 없는 상태에서는 추측을 줄이고 한계를 알려야 합니다.

### 부분 실패와 전체 실패를 구분해야 함

맛집 검색 하나가 실패했다고 여행 지역 추천까지 버리는 대신, 가능한 결과를 유지하고 경고를 추가하는 방식이 사용자에게 더 유용했습니다. 반대로 필수 날짜나 AI 지역 추천이 실패하면 이후 단계를 진행하지 않는 기준도 필요했습니다.

### 작은 이름 불일치가 전체 기능을 막을 수 있음

`style`과 `styles`의 차이처럼 HTML 속성 하나가 JavaScript 수집과 백엔드 입력 전체를 끊을 수 있습니다. 화면만 확인하지 않고 요청 payload와 각 단계의 로그를 함께 확인해야 원인을 정확히 찾을 수 있었습니다.

### 로컬 성공과 배포 성공은 다름

로컬 서버, Vercel 로컬 도구, Production은 서로 다른 실행 환경입니다. 배포 후 실제 URL에서 메뉴, 반응형, 환경 변수, API 요청, 오류 문구를 다시 확인하는 과정까지 구현의 일부임을 배웠습니다.

### UX도 기능의 일부임

로딩 상태, 중복 클릭 방지, 선택 해제, 사용자용 오류 문구, 다크 모드, 모바일 메뉴, 모션 감소 설정은 AI 응답만큼 실제 사용성에 영향을 주었습니다.

## 18. 발표 핵심 정리

이 프로젝트의 핵심은 AI 호출 자체보다 다음 전체 흐름을 웹 서비스로 완성했다는 점입니다.

```text
사용자 입력
→ 프론트엔드 검증과 상태 표시
→ Python 백엔드와 환경 변수
→ AI 지역 추천과 JSON 검증
→ 실제 장소 데이터 보강
→ AI 일정 구성과 재검증
→ 사용자에게 결과·경고·오류 표시
→ 실제 Vercel 환경에서 재확인
```

구현 과정에서는 축제 테마 누락, 날짜와 맞지 않는 축제, 반복 장소, 동행 선택 해제, 로컬·배포 환경 차이 같은 문제를 겪었습니다. 이를 통해 AI 결과를 그대로 믿는 것이 아니라 입력 전달, 외부 데이터의 성격, 응답 검증, 실패 처리, 사용자 안내까지 함께 설계해야 실제 서비스가 된다는 점을 확인했습니다.
